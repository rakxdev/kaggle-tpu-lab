Qwen-Image-2.1 API

Full-precision text-to-image generation. Submit a prompt, hold your place in a queue that never rejects a request, and fetch your image when a worker frees up. Three GPU workers, one shared queue, zero rejections.

Overview

The service runs the complete, unquantized Qwen-Image-2.1 model (33.1 GB BF16) on an NVIDIA H200 across three worker processes. Every generation request is admitted to a durable FIFO queue — at any traffic level the response is either a finished image or a queue position, never a rejection.

PropertyValue
ModelQwen-Image-2.1 — 7B DiT + Qwen3-VL 8B encoder, full BF16
Resolutions64–2048 px per side, multiples of 32 (native 2K supported)
QueueUnbounded FIFO — requests wait, never fail
Workers3 concurrent renders
Result retention24 hours after completion
LicenseQwen Research — non-commercial research and evaluation
The golden rule of this API: a submit can only fail validation (bad key, bad parameters). Capacity is never a failure — when all workers are busy, you get a queue position and your turn comes in order.

Quickstart

Three calls: submit, poll, download.

1 · submit 
curl -s -X POST https://pseudoasymmetric-unbodied-sabine.ngrok-free.dev/generate \
  -H "Authorization: Bearer YOUR_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"a lighthouse in fog","width":1024,"height":1024,"steps":28,"seed":7}'

# → 202
# {
#   "job_id": "e7d850545110…",
#   "status": "queued",
#   "queue_position": 0,                       ← 0-based; you are #1
#   "status_url":  "/jobs/e7d850545110…",
#   "result_url":  "/jobs/e7d850545110…/result",
#   "cancel_url":  "/jobs/e7d850545110…/cancel"
# }
2 · poll until done 
curl -s https://pseudoasymmetric-unbodied-sabine.ngrok-free.dev/jobs/JOB_ID \
  -H "Authorization: Bearer YOUR_KEY"

# while waiting:
# { "status": "queued",    "queue_position": 1,  … }
# { "status": "rendering", … }
# when finished:
# { "status": "done",
#   "result": { "seed": 7, "width": 1024, "height": 1024,
#               "steps": 28, "seconds": 4.3,
#               "seconds_per_step": 0.154, "fast": false },
#   "result_url": "/jobs/JOB_ID/result" }
3 · fetch the PNG 
curl -s https://pseudoasymmetric-unbodied-sabine.ngrok-free.dev/jobs/JOB_ID/result \
  -H "Authorization: Bearer YOUR_KEY" -o image.png

Authentication

Every endpoint except /health and /queue requires a bearer token. Send it in the Authorization header; a missing or wrong token returns 401.

Browser clients: requests made from JavaScript must also send the ngrok-skip-browser-warning: true header to bypass the tunnel's first-visit interstitial. Server-side clients (curl, SDKs) don't need it.

Submit a generation

POST/generate

Adds a job to the queue and returns immediately with its position. The queue is unbounded — this endpoint does not have a capacity-based failure mode.

Request body

FieldTypeDefaultDescription
promptstringrequired What to draw. Minimum length 1.
widthint1024 64–2048. Must be a multiple of 32 (values are floored).
heightint1024 Same rules as width. Total pixels are capped at 2048×2048.
stepsint20 1–50. Cost scales linearly; more steps refine detail. 28 is a good balance.
cfgfloat1.0 Guidance scale. The model is guidance-free at 1.0 — that is the intended full-quality setting. Above 1.0 the model runs twice per step (2× cost).
seedint-1 -1 picks a random seed, which is returned in the job status. Same seed + same parameters = same image.
negative_promptstring"" Only used when cfg > 1 — the pipeline ignores it at the default setting, so the server drops it rather than pretending it was applied.
fastboolfalse Opt-in distilled lane: forces 8 steps and cfg 1.0, roughly 4× faster. Trade-off: dense text and complex compositions degrade. See Fast lane.

Response — 202 Accepted

application/json 
{
  "job_id": "e7d850545110…",
  "status": "queued",
  "queue_position": 0,
  "status_url": "/jobs/e7d850545110…",
  "result_url": "/jobs/e7d850545110…/result",
  "cancel_url": "/jobs/e7d850545110…/cancel"
}

queue_position is a snapshot at submit time (0-based — position 0 means you are next). Re-poll status_url for the live value.

OpenAI-compatible endpoint

POST/v1/images/generations

Same parameters as /generate, but the call stays open for up to 120 seconds and answers with the OpenAI images shape — so the official OpenAI SDK works unmodified. If the queue is deeper than the wait, it returns the same 202 envelope as /generate and you fall back to polling.

python — official SDK 
from openai import OpenAI

client = OpenAI(
    base_url="https://pseudoasymmetric-unbodied-sabine.ngrok-free.dev/v1",
    api_key="YOUR_KEY",
)
img = client.images.generate(model="qwen-image-2.1", prompt="a lighthouse in fog")
open("out.png", "wb").write(base64.b64decode(img.data[0].b64_json))
Extras beyond the OpenAI schema arrive as top-level keys: seed, seconds, seconds_per_step, fast, job_id. OpenAI clients ignore them; you can use them.

Job status

GET/jobs/{job_id}

Live state of one job. Poll this while waiting.

Lifecycle

queued→ rendering→ done
queued→ canceled (cancel only works in this state)

Response fields

FieldPresentDescription
statusalwaysqueued · rendering · done · error · canceled

Fetch the image

GET/jobs/{job_id}/result

Returns the finished image as PNG bytes. Available for 24 hours after completion. 409 if the job hasn't finished, 410 if the result expired, 404 for an unknown id.

Cancel a job

POST/jobs/{job_id}/cancel

Removes a job while it is still waiting. Returns 200 on success, 409 if rendering already started. A canceled slot frees up for the next job in line.

Queue lobby

GET/queue

Global counts, no authentication. Handy for a status badge.

response

Queue semantics

The queue is the contract. These properties are enforced by design and have been verified under load:

PropertyBehavior
Never rejectsNo capacity-based errors exist. An unbounded number of jobs can wait; each is ~300 bytes of state.
Strict FIFOThe oldest queued job takes the first free worker. Positions are recomputed on every poll — always fresh, never drift.
VRAM-awareA job only starts when the card genuinely has room for its size. Large renders (2K) wait for a calm card instead of failing; small renders behind them keep flowing.
Crash-proofJobs live in a durable store. A worker that dies mid-render has its job requeued automatically (up to 6 attempts). Pending jobs survive server and Studio restarts.
Disconnect-proofClosing your connection changes nothing. Poll again later with the same job id — the result waits up to 24 hours.
Serializable big rendersAt full settings, 2K renders run one at a time by design; smaller renders can slot into the remaining memory alongside them.

Fast lane

Setting "fast": true routes your request to a distilled Turbo8 adapter: 8 steps instead of 20–50, roughly 4× faster (~1.5 s per 1024² image). The server forces 8 steps and cfg 1.0 on this lane and ignores contradicting parameters.

The trade-off is real and measured: overall prompt adherence holds, but dense or small text inside the image degrades (character accuracy drops from ~99% to ~95%, exact text match from 95% to 75%). Use fast mode for exploration and drafts; use the base lane for final renders and anything with legible lettering.

Error codes

CodeMeaningWhat to do
400Invalid parameters (e.g. pixel cap exceeded)Fix the request
401Missing or wrong bearer tokenSet the Authorization header
404Unknown job idCheck the id
409Job not finished (result fetch) or already rendering (cancel)Poll until done; cancel only while queued
410Result expired (24 h)Generate again
422Parameter failed validationThe response names the field
500Render failed server-side (rare; e.g. repeated OOM)Retry once, then report
503fast requested but the fast lane isn't loadedDrop fast or wait for the operator

A transport drop (timeout, connection reset) is never a verdict — the job stays in the queue. Poll again with the same id.

Measured performance

Real numbers from this deployment (H200, full BF16, warm). Per-image cost at $3.82/h is about $0.006 at 1024²/40 steps.

SettingRender timeRate
512² · 20 steps~0.9 s0.05 s/step
1024² · 20 steps3.0 s0.15 s/step

2048² · 20 steps15.8 s0.79 s/step
2048² · 50 steps (max)~42 s0.85 s/step

Under burst the workers share the GPU, so concurrent renders each run slower while total throughput rises — a measured 5-way burst of 512²/20 sustained 51 images/min with every request served.
